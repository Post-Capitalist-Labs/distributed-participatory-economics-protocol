## 1. Evaluation of the Four Candidate Architectures

We compare the four architectural paradigms specified in Section 5 of the Research Brief:
- **Architecture A — Conventional Distributed Services:** Federated PostgreSQL/SQL databases, REST/gRPC authenticated APIs, replicated cloud/community servers, and event-driven message brokers (Kafka/NATS).
- **Architecture B — Pure Peer-to-Peer Distributed Protocol:** Content-addressed data (IPFS/Iroh), DHT/mDNS peer discovery, libp2p gossipsub, authenticated messages, and CRDT state replication without a global consensus layer.
- **Architecture C — Blockchain / Distributed Ledger:** Application-specific Byzantine Fault-Tolerant (BFT) blockchain (e.g., Cosmos SDK / CometBFT or Narwhal-Bullshark DAG ledger) processing all council proposals, votes, price updates, and intra-year consumption transactions on-chain.
- **Architecture D — Hybrid Local-First + P2P Federated + Selective Epoch-BFT Architecture (Recommended):** Local-first SQLite/CRDT clients (`Role-LP`), peer-to-peer council/federation coordination (`Role-CC`), hierarchical Merkle-Sum Tree (MST) aggregation (`Role-PCW`), and a lightweight rotating BFT checkpoint layer (`Role-BFT`) invoked only for round finality, deterministic WASM IFB verification, and macro Society Account settlement.

## 2. Granular Assessment of Candidate Technologies

Not all decentralized technologies are equally mature or mutually compatible. Below we evaluate each technology listed in Section 5, specifying whether to **Adopt**, **Adapt Selectively**, or **Reject** for DPEP:

| Technology Category | Specific Candidates Evaluated | Maturity (2026) | Compatibility & Overhead Assessment | Decision for DPEP |
| :--- | :--- | :---: | :--- | :--- |
| **P2P Networking & Content Addressing** | `libp2p` (Rust/Go), **Iroh** (`quinn` QUIC + BLAKE3 verified streaming), IPFS (Kubo) | High (`libp2p`, `iroh`); IPFS DHT is heavy | Classic IPFS global Kademlia DHT has high latency (2–10s lookups) and high battery drain on mobile. **Iroh** (QUIC hole-punching + relay servers + BLAKE3 verified streaming) or scoped `libp2p` over QUIC is far lighter and mobile-friendly. | **ADOPT Iroh / `quinn` (QUIC) + BLAKE3 verified streaming** for Layer 2; avoid global public IPFS DHT. |
| **CRDTs & Local-First Storage** | **Automerge 2+**, **Loro**, Yjs, SQLite (`rusqlite` / SQLCipher) | High | Storing 100,000 numerical planning iterations inside a general-purpose text/JSON CRDT causes metadata bloat. CRDTs excel at **collaborative council documents, qualitative `Lists`, and BJC rosters**, while **SQLite** excels at relational/vector accounting and historical price queries. | **ADOPT Hybrid Local Store:** SQLite for structured vectors, prices, and accounting ledgers + Loro/Automerge CRDTs for council deliberation drafts and qualitative `Lists`. |
| **Event Sourcing & Merkle Structures** | Append-only signed event logs; **Sparse Merkle-Sum Trees (MST)** over BLAKE3 | High | Standard Merkle trees prove membership of a proposal but *not* that the sum of all leaves equals the reported aggregate supply/demand. **Merkle-Sum Trees** bind non-negative vector sums directly into every parent hash, preventing phantom supply/demand injection. | **ADOPT BLAKE3 Sparse Merkle-Sum Trees** as the core cryptographic primitive for Layer 2 federated aggregation. |
| **BFT Consensus Protocols** | **CometBFT** (Tendermint), **HotStuff / Simplex**, Bullshark/Narwhal (DAG-BFT), Raft (CFT) | High (CometBFT); Medium-High (HotStuff/Simplex) | DAG-based BFT (Narwhal/Bullshark) is designed for 100,000+ TPS continuous mempool streaming, adding massive complexity for a system that only needs ~10–20 epoch checkpoints per planning cycle. CometBFT or a minimal 2-step **Simplex/HotStuff** engine is simple, deterministic, and supports instant finality. | **ADOPT CometBFT (or lightweight Simplex BFT)** strictly for Layer 1 Epoch Checkpoints (and allow simple threshold-signed federation checkpoints in single-region PoC). |
| **WASM Runtimes** | **Wasmtime** (Bytecode Alliance), Wasmer, `wasm32` browser target | Very High | Floating-point operations (`f32`/`f64`) can have non-deterministic NaN/rounding behavior across CPU architectures. By restricting economic WASM modules to **64-bit/128-bit fixed-point integer arithmetic** and running in `Wasmtime` with deterministic fuel metering, every node gets bit-for-bit identical prices. | **ADOPT Deterministic Fixed-Point WASM (`Wasmtime`)** for IFB price-update rules, $SB/SC$ checks, and council constraint validation. |
| **Zero-Knowledge Proofs (ZKPs)** | **Bulletproofs** (Discrete Log), **Plonky2 / Plonky3 / RISC Zero** (FRI / Hash-based STARKs), Groth16 | Medium-High | Pairing-based SNARKs (Groth16, PLONK over BN254/BLS12-381) and discrete-log Bulletproofs are **broken by quantum computers (Shor's algorithm)** and Groth16 requires a trusted setup. Hash-based **FRI/STARKs (`Plonky3` / `Winterfell`)** or **Lattice-based ZKPs** are post-quantum plausible and need no trusted setup, though proof sizes are larger (~20–100 KB). For simple budget proofs ($P \cdot y_u \le B_u, y_u \ge 0$), a lightweight hash/lattice range proof or blinded council tally is sufficient. | **ADOPT Selectively:** Use hash-based STARKs (`Plonky3`) or lattice commitments ONLY for individual private consumption budget compliance ($P \cdot y_u \le B_u$); do **not** wrap global planning iterations in massive ZK-VMs. |
| **Secure Multiparty Computation (MPC) & Threshold Crypto** | Shamir Secret Sharing, FROST (Schnorr), **Lattice-based Threshold Signatures / Additive Homomorphic Masking** | Medium (Lattice threshold is emerging) | Full general-purpose MPC across 30,000 councils has prohibitive round-trip network fragility if any node drops offline. However, simple **pairwise additive masking (Bonawitz-style Secure Aggregation)** inside a 100-person neighborhood council allows summing $y_h^{\text{priv}} = \sum_u y_u^{\text{priv}}$ without any neighbor seeing $y_u^{\text{priv}}$! | **ADOPT Bonawitz-style Pairwise Additive Masking + Commitments** for intra-neighborhood private demand aggregation; reject general-purpose economy-wide MPC. |
| **Decentralised Identity & Authorization** | W3C DIDs (`did:key` / `did:webvh`), **UCANs** (User Controlled Authorization Networks), Anonymous Credentials (BBS+ / PQ-Blind Signatures) | High | Token-based or blockchain-registry DIDs create unnecessary dependencies. **PQ-adapted UCANs** (chained capability tokens signed with ML-DSA) naturally express Parecon's institutional hierarchy: a Council accredits a Delegate with a time-bounded capability certificate, revocable by the Council. | **ADOPT PQ-UCAN Capability Certificates** for council membership and revocable federation delegation + **Blinded Effort-Budget Credentials** to unlink workplace identity from personal consumption items. |

### Recommended Polyglot Stack Decision
1. **Core Protocol, Cryptography, MST Aggregation, Local Solver, and Node Daemon (`dpep-core` & `dpep-node`):** **Rust** (compiled both natively for `Role-CC`, `Role-PCW`, `Role-BFT` on Linux/Raspberry Pi/macOS and to **WASM** for deterministic IFB execution). Note that **Clarabel.rs** (an interior-point conic/quadratic solver written in 100% safe Rust) and **HiGHS** allow every council and household client to solve constrained convex optimization problems locally in milliseconds!
2. **Mobile & Desktop Cross-Platform Client Library:** Expose `dpep-core` via **Mozilla UniFFI** (for native Kotlin/Swift bindings where hardware keystore access is needed) and **WASM** for a **TypeScript Local-First Progressive Web App (PWA)** that runs on any smartphone, tablet, or desktop browser without app-store gatekeeping.
3. **Epoch BFT Checkpoint Layer (`Role-BFT`):** Integrate with **CometBFT (Go)** via ABCI 2.0 (or a lightweight embedded Rust BFT engine) in production, while using a simple deterministic threshold-signed epoch coordinator in the initial Proof of Concept.
